# Plan de Entrega 1 · PIA-3

## Objetivo y alcance

Entregar un sistema que conviva con el simulador oficial, procese y confirme partes de recorrida por voz, detecte anomalías en planta y emita alertas de seguridad aun con el enlace caído. La entrega incluye tools de solo lectura, MCP, PostgreSQL 16 con pgvector, evaluación de retrieval y documentación técnica.

Este plan es la fuente de seguimiento del proyecto. Los Issues de GitHub organizan el trabajo y contienen sus propios criterios de aceptación. La [arquitectura](ARQUITECTURA.md) describe el sistema y el [registro de decisiones](DECISIONES_TECNICAS.md) conserva las razones de las decisiones.

## Eliminatorias y dependencias

- **Eliminatorias.** Se superaron en las corridas de los Issues #9, #11 y en la fase 5B del #13. Una futura corrida debe verificar los cambios en arranque del modelo, conexión MQTT, detector, deduplicación y outbox que puedan afectar el resultado.
- **Corrida reproducible.** Se registraron los SHA del agente y del simulador y la identidad de la imagen. El corrector oficial usa el proyecto `planta` y requiere puertos libres. Las próximas corridas deben mantener los volúmenes de evaluación separados y usar una ruta de resultados nueva.
- **Contratos y datos.** Usar el paquete oficial instalado y las APIs de planta e historian. Mantener `/api/verdad` separada del runtime. Confirmar la versión y configuración del STT en la lista autorizada.
- **Capacidad.** La muestra histórica del agente en reposo fue de aproximadamente 203 MiB. Los límites efectivos del agente y PostgreSQL suman 3 CPU y 3 GiB. Queda medir el consumo bajo carga cuando se incorporen memoria y recuperación.

## Riesgos conocidos

- **Arranque sin Internet.** La corrida observada hizo peticiones a Hugging Face antes del primer latido. Un volumen de modelos vacío o una condición de enlace adversa puede dejar al agente sin inicializar.
- **Demora y regresiones de seguridad.** Las colas son secuenciales. Descarga, STT y acuses comparten el presupuesto de 30 s. Los tests de texto cubren frases elegidas y aún falta comprobar la robustez con voz de campo.
- **Persistencia y recepción.** MQTT entra con QoS 0 por defecto. La recuperación protege las notas ya guardadas. IDs repetidos entre corridas pueden omitir una nota y QoS 1 puede provocar reenvíos tras una confirmación local incompleta.
- **Versiones.** El contrato se instala desde una referencia Git sin SHA fijado. El desfasaje de imagen observado muestra por qué conviene registrar la versión instalada y la imagen de cada prueba.
- **Memoria del parte.** El contrato `FilaParte` tiene `tag`, `variable`, `valor`, `unidad` y `observacion`. El diseño del parte persistido debe representar hora y asociación de fotos y conservar la validez del payload oficial de la tablet.
